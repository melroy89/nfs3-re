# Braking assist gameplay behavior

## Setting path and mode selection

The installed `level.mnu` option uses list key `braking`. As documented in [gameplay-assist-menu-crosswalk.md](gameplay-assist-menu-crosswalk.md), list ordinal 0 is Off and 1 is On; its persistent menu-selection storage is `006fd474`. The regular-race roster builder (`BuildRegularRaceRoster`, `00473bf0`) copies this selection to effective runtime flag `006fd490` at `00473c36..00473c3b`. That copy is the point at which the menu choice becomes the regular-race control flag; it does not prove which choice is loaded in a running session.

Other builders override the selection. `BuildRaceModeTwoRoster` (`00473ee0`) and `BuildRaceModeOneRoster` (`00474310`) each zero `0x1c` bytes starting at `006fd490`, covering all effective assist flags, through `ZeroMemoryRegisterCall` (`004e070c`). `BuildHotPursuitRoster` (`00474640`) explicitly writes zero to effective assist flags `006fd490..006fd4a4` (the six fields through traction). Consequently a saved/menu On value is not enough to activate this assist in those roster paths. Some profile-adjustment branches also require player-mode global `006fd3b0 < 2` and race-mode global `006fd3b8` not equal to 1 or 2; these numeric values are left in their observed code domain here.

## Concrete effects in eligible ordinary gameplay

There are two direct gameplay paths for effective flag `006fd490`:

1. **Shared automatic track-speed control.** `UpdateVehicleSmoothedControlsAndModeState` (`004a9bc4`) enters the controller when either effective Braking (`006fd490`) or Steering (`006fd494`) is nonzero, subject to its vehicle-role/state gate. The sole direct call to `004a83d3` is at `004a9d1d`. Thus Braking On alone is sufficient to select this shared controller, although its control law also supports Steering and is not an exclusively braking-only routine.

   The controller derives an adjusted track-speed target from the track speed sample and heading modifier, compares it with current vehicle speed, and forms a target control from the current acceleration/brake inputs (`vehicle+0x504` and `+0x505`). The target is `256 + accel - brake`; state `vehicle+0x218` approaches it by at most 32 units per controller call. The gear-specific speed-to-RPM ratio and the profile's idle/redline endpoints then form a signed integer quotient used to choose coasting, gas, or brake output. The effect appears in throttle byte `vehicle+0x508` and brake byte `vehicle+0x509`. Under the finite, valid-index conditions in [controller-quotient-contract.md](controller-quotient-contract.md), quotient `<= -1` yields gas 0/brake 255; quotient 0 coasts or follows the requested input around the target; quotient `>= 1` follows the smoothed requested control. This is a computer-applied speed/cornering aid consistent with the installed help text “Slows car for better cornering.”

2. **Per-vehicle profile adjustment during setup.** The sole direct caller of `004a78d6` is vehicle initialization at `0042c3c8`, after the selected profile has been loaded. In the eligible mode branches, the helper tests `006fd490` directly. CARP token/field evidence identifies physics-profile float `+0x1dc` as `frontbia` (front brake bias) and float `+0x254` as `gtransfe` (G transfer factor). The Braking branch adds `+0.05` to `frontbia`; the earlier profile/track adjustments are then bounded to `0.30..0.75`. It adds `-0.05` to `gtransfe` after the preceding profile adjustment and clamp path. These are per-vehicle setup-time physics values, not samples of the driver's braking pedal. The latter field is not followed by another clamp in this Braking branch.

The two effects answer different questions: `004a83d3` actively adjusts control outputs from track-relative speed/RPM, while `004a78d6` adjusts physics-profile parameters when an eligible vehicle is initialized. The first is the concrete automatic gas/brake aid; the second changes front brake bias and weight-transfer response. The report does not assign broader design intent to the latter beyond the decoded field names and arithmetic.

## Distinction from CARP `usesanti`

`usesanti` is a separate per-car physics-profile byte parsed from CARP field 17 at profile offset `+0x1d4`. When its preceding wheel-response conditions hold and vehicle byte `+0x50d` is zero, the planar-response helper clamps a composite wheel-response scalar to the profile capacity and marks the response record. It is not read from menu global `006fd474` or effective flag `006fd490`, and the Braking menu option is not the CARP parser's `usesanti` field. The existing `usesanti` audit therefore describes a conditional anti-lock-related response limiter, whereas this report describes a player-facing driving assist that also drives track-speed-based gas/brake control. The code does not prove complete physical ABS behavior or a separate PC ABS toggle.
