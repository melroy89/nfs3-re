# Network roster count to race initialization: capacity and admission audit

## Scope and evidence class

Static, instruction-grounded analysis of the installed `nfs3.exe` (PE x86, SHA-256 `2a20f80465ed53d320f1a6f41c9dde2c07de0bc5525af1f23f8e6aff3e6181fb`) in an ephemeral REA/Ghidra 12.1.4 session. No executable was run or modified, and no persistent Ghidra project was edited. The source-selection and capacity claims below are static. They do not establish sender behavior, packet delivery, runtime reachability, or allocation validity beyond explicit extents decoded in the initializer.

The field chain is:

`wire signed WORD 007a2276` → race-roster builder → derived counts `006fd514` (humans) and `006fd510` (total configured participants) → `InitializeRaceVehicles 0042c700`.

The wire count and derived builder totals are distinct fields. Builder totals are outputs, not admission checks.

## Upstream admission and normalization evidence

### Type-1 control packet path

`InstallNetworkConnectionCallbacks` (`004a6410`) installs dispatcher `004a6440` at connection record `+0x20`; its handler-table type-1 entry at `0055ecc0` is receiver `004a68d0` as recorded in `analysis/network-roster-admission.md`. At `004a6440`, the dispatcher reads the packet type byte and makes the indirect table call only when session-abort WORD `007a22dc` is zero and the type byte is `< 0x13`. It receives no length argument at this gate and has no fixed-roster-size check (`objdump -D -Mintel`, `004a6440..004a646d`). This gate selects/dispatches the handler; it does not validate the roster count.

Receiver bytes at `004a68d0` (`ev_2992d84d626b3af776eeed1dd08d6f1e70cf12f12bd98bd3c21f439107d4170c`) show these steps:

- If `007a2210` indicates the first invocation has completed, enter the transport lock; then clear eight remote active WORDs at indices 1 through 8 (`007a22ca..007a22d8`). Index 0 (`007a22c8`) is deliberately skipped in this clear loop.
- Copy exactly `0x7c` bytes from the packet pointer to `007a2214` and set roster-changed WORD `007a2296` to 1. The count at packet offset `+0x62` therefore reaches `007a2276` unchanged; this copy is not a count clamp.
- Only when transport DWORD `007a22e4 == 2`, loop exactly eight ID positions. For each ID unequal to local ID (`004a5af0`), compare the loop index against the sign-extended count at `007a2274 >> 16`; mark its endpoint active if `index < signed_count`, otherwise inactive. The fixed index loop caps endpoint-row writes at eight, but the code leaves the signed count itself untouched. A count above eight can therefore remain above eight after only eight row iterations; a negative count compares below every nonnegative index and marks all processed entries inactive.

The locally constructed roster has a tighter, directly visible domain. `BuildAndBroadcastNetworkParticipantRoster` (`004a66c0`, `ev_70a8bc1dda3028dbc13def115ca8e36292254e083d247fa0c2f895591f0af749`) stores count 1 at `004a66f1`, then scans remote row indices 0..6 (`CMP index,7` at `004a6735`). Each active endpoint can append one ID/name and increments the WORD at `007a2276` at `004a67e0`. For stable row state this producer emits **1..8**, including its initial local participant. This is evidence for locally built packets only; it is not a receive-side invariant.

### NPS host admission is a separate, incomplete bound

The incoming connection event handler `004a5e50` queues host event `0x203` only in the host-role branch (`007a22da != 0`) and when the peer ID differs from local user ID (`007a20a0`); its client-role event `0x203` path instead initializes local endpoint 0 after the event's success byte check. The host queue producer `TryQueueNetworkAdmissionRequest` (`0049e320`, `ev_728dfbd9bd36b20f28be7a671406f4887c3efd4bc4572dd8b57f7cbccf128d73`) additionally requires global gate `0055e710 == 0` and reservation count `007a01e0 < 7`; it increments that count before enqueue. The queue writer at `0049f6a0` wraps its write cursor modulo six and does not itself reject a full ring (`ev_78c3d25c8345be324a1ed0591e1fa57403b85567eb300c4996b18374a543e7ea`).

`ServiceHostNetworkAdmissions` (`0049eae0`, `ev_f9fd13fbb7348240b477c34de311b441d5be80bcaf4c3b179b74de73336c9f0d`) runs only in network state 3 and host role. It scans endpoint active flags at indices 0..7. If all are active, the signed slot becomes 8 and falls through to name copy and `InitializeNetworkParticipantEndpoint` (`0049efb0`) without rejection. That initializer sign-extends DX and calculates `007a22e8 + slot*0x6c` with no local bounds check (`ev_ce3c93ed2ef6fb976602f5213d383f9c8e10f8d010344321e939a3a3e3ab544a`). After transport-2 setup, or after the other transport's connection method `0xd2` succeeds, the host service increments WORD `007a2276` (`0049ec23`); the failure path instead decrements the separate reservation counter. The `<7` reservation gate is not compared to the active-flag scan or to the wire WORD here. Existing notes also show that `CloseNetworkParticipantConnection` releases reservations, but no static invariant ties that lifecycle exactly to all active flags and advertised-count writes.

Therefore a local producer can be bounded to eight, but host event admission does not independently prove `007a2276 <= 8` in all states. The slot-8 fallthrough is an explicit gap in the host-side bound, not a claim of a reachable runtime overflow.

## Builder selection and signed-count gates

`00474ca0` dispatches one of four builders using selector `006fd3b8`: regular `00473bf0`, mode one `00474310`, mode two `00473ee0`, or pursuit `00474640` (`ev_574876a8bf91c9909028eede8fe6b0e7e68a63eb35c6ca3100390cb6e30100d8`). Each builder's roster-mode switch uses `006fd3b0`; modes 2–4 take the network-count branch. Other branches synthesize local/split-screen rows and are outside this network-count chain.

Across the network branches, the count is read from the containing DWORD at `007a2274` then arithmetically shifted right 16. Loop tests are signed `index >= count`; there is no local lower- or upper-bound test before deriving/writing setup rows. For a negative count, these network loops perform zero iterations. For a positive count, they can process every value up to that signed WORD's positive range unless an individual builder has another per-row filter. The 8-entry identity lookup in mode-one/mode-two builders can reject an individual ID (`004a6690` scans entries 0..7 and returns `-1` otherwise, `ev_7e5bce8f87ebc347a76d9d23d2e215d7e4181a8d937e9df9a30860bc9e0222ca`). Under stable table contents and a nonrepeating ordinal, at most eight ordinals match and are accepted; the outer loop work itself remains bounded only by the signed advertised count.

Regular and pursuit builders write one setup row per positive advertised N, so their row-write bound remains unresolved until upstream count admission or the setup array extent is established.

## Sixteen-record initializer

`InitializeRaceVehicles` (`0042c700`) is reached from `004283d0` only after the three earlier setup steps return without setting error DWORD `0055e88c`; the fourth stage checks that error again after returning. This call chain provides error-abort gates, but no participant-count admission test.

At entry, `0042c700` clears `0x9ac0` bytes beginning at `005e1120` and `0x4ac0` bytes beginning at `005eabe0`, then begins its first loop with `ECX=0` and exits only when signed `ECX >= [006fd510]` (`0042c729..0042c746`). It computes participant-indexed offsets using strides `0x9ac` and `0x4ac`, calls initialization helpers and writes vehicle field `+0x220`. Its second loop likewise processes `EDX=0..006fd510-1` without a local clamp (`0042c7c1..0042c7db`). Arithmetic gives exact capacities of **16 rows** for each cleared span: `0x9ac0 / 0x9ac = 16`, `0x4ac0 / 0x4ac = 16`. There is no local test for `<16` before either loop. This proves the cleared physical spans' extent and loop behavior; it does not independently prove the backing extent of every indexed helper table, the `0x6c`-stride setup-row source, or the vehicle-pointer bank.

For the two named spans, the sufficient count condition is `0 <= g_nConfiguredParticipantCount <= 16` on normal completion, plus successful callees and valid indexed inputs. The initializer itself enforces none of these. If the count is negative, signed loop checks skip; this is not a valid roster claim. A value above 16 passes the last in-span row and iterates beyond both cleared spans. This condition says nothing about the separate `0x6c`-stride setup-row source that builders populate before initialization.

## Supported valid-domain conclusion and blockers

The **common sufficient producer-domain** is `1 <= signed roster count <= 8`: the only fully observed bounded constructor starts at one and adds at most seven active remote positions. Under that precondition, regular and pursuit builders each write at most eight network rows, while mode-one and mode-two create at most eight rows because their nonrepeating ordinals can match only entries in the stable eight-WORD identity table. Regular selector 1 and pursuit's human-police/minimum-AI branch can produce nine configured participants; mode one configures eight, and mode two starts at eight or fewer before its unchecked reduction. These configured totals fit the initializer's two explicit 16-record buffer capacities. This demonstrates a sufficient condition, not that all valid peers actually satisfy it.

The receiver breaks the proof chain: fixed-size copying preserves arbitrary signed WORD bits; no receive-side normalization or positive/range check was observed; the transport-2 eight-ID pass does not reduce the stored WORD; and the host admission counter does not gate the full-slot fallthrough or compare its state with the roster total. Consequently, the shipped instructions do **not** establish that `N` remains in 1..8 before the builders. Exact universal safe maximum for each builder cannot be called a valid network-domain rule from the current evidence. The `0..16` condition applies only to the initializer's explicitly cleared buffers; mode-specific setup descriptor backing extent remains unproven. Transport-1 host-frame construction adds a separate concern: its 32-byte frame writer loops over `006fd514` and writes four bytes per human at `004c6870..004c6956`; the caller sends the whole 32-byte area, so counts above eight exceed the frame's visible row area. The caller and loop evidence are already documented at `analysis/detailed-analysis-notes.md:4077-4081`.

No runtime packet tests, external NPS provider guarantees, sender authorization/framing contract, or storage-boundary behavior were assessed. The result is a static admission gap with exact local sufficient bounds, not a demonstrated malformed packet, runtime overflow, or gameplay defect.
