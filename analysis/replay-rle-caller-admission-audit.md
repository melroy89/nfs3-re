# Replay RLE caller and admission audit

## Scope and result

This read-only static pass traces the installed `nfs3.exe` (SHA-256 `2a20f80465ed53d320f1a6f41c9dde2c07de0bc5525af1f23f8e6aff3e6181fb`) from vehicle control callbacks through replay recording/playback, the RLE wrapper, fixed storage, and `.rp3` file read/write. It supplements the token arithmetic in [detailed-analysis-notes.md](detailed-analysis-notes.md#replay-rle-malformed-token-count-bound) and the bounded output probe [replay-rle-token-bound.json](evidence/static/replay-rle-token-bound.json); it does not repeat token encoding identity. No game execution, runtime capture, executable modification, or persistent Ghidra edit was made. The ephemeral REA session was closed without a snapshot.

**Finding:** Recording has a concrete producer and a one-time output reservation check. Playback has a concrete fixed maximum file read and fixed per-channel output staging, but the decoder receives no actual file-byte count or compressed-stream extent. Header counters describe fixed replay metadata/other fields and are not used as the decoder's input limit. Therefore safe admission is conditional on valid participant/sample indices, a complete stream within the bytes actually read, and per-channel token runs that stay within the intended 32-byte channel staging extent. Those conditions are not all enforced on the path traced here.

## Caller and source chains

### Recording

1. `InitializeVehicleUpdateCallbacks` (`0042c400`, `ev_29821e5495ad51f8d5c35b7b74efeb8863801b9e95d94eca78c43956b93ca3d1`) stores lifecycle/control callback address `004bd380` at vehicle/object offset `+0x5fc`. A flag-bit branch can clear that callback for selected objects; a network-associated branch changes other callbacks but leaves the default `+0x5fc` assignment in place.
2. The control path invokes this callback at `0043145c` (recorded previously in detailed notes section 2330). The callback at `004bd380` takes its participant index from object `+0x1f4`. For replay state `0` or `1` it calls `004bd000`; for state values above `1` it calls playback helper `004bd090` (`ev_de4a44ddcac54661b48dbfd495c013fc4d4223defbcfacd70323aa719469766f`; xref to `004bd090` is at `004bd3d2`). The callback has no local participant-index range check.
3. Recorder `004bd000` calls `0048f6a0`, then appends four current action bytes from `0079c4a8..0079c4ab` into the participant row at `007cd548 + participant*0x80`. Its four channel offsets are `0x00`, `0x20`, `0x40`, and `0x60`. Each channel counter is the DWORD at `007a3e30 + participant*4`; the ordinary path increments it once per sample and flushes when it reaches `0x20`, then resets it to zero (`ev_9be253355e4d88011cedbe81f40167ac79f80e2477666cd34a6e3137a06e44af`). Thus a normal flush supplies exactly 32 bytes per channel, collected into a 128-byte caller stack block, to `004bcda0`.
4. `004bcda0` makes one preflight check, `007cda50 + 0x80 < 0x1e000`. On failure it sets error state and performs no four-channel append. On success it encodes each 32-byte channel and appends the returned encoded byte count, advancing `007cda50` after each append (`ev_e93b6c3f695c59cb6ca1ab645b9cf2ecc8bf988bd4f8d41affb460c5851ce086`). The initialized output stream begins at `007a5f48` and has nominal extent `0x1e000` ending at `007c3f48`. The guard reserves 128 bytes for a four-channel block, while the existing probe establishes a possible combined encoded length of 176 bytes. Consequently the guard alone is sufficient only when the actual sum of the four encoded lengths fits the remaining extent; it is not a full worst-case reservation.

**Conditional safe recording domain:** the callback's `+0x1f4` index addresses a valid participant row/counter; its sample counter enters each flush in `0..31`; and `007cda50 + sum(encoded lengths) <= 0x1e000`. Normal 32-sample batching is established locally. The callback index's upstream admission and the final encoded-length-versus-remaining-capacity relation are not locally checked by these routines.

### Playback

1. `004bd090` is reached by the same `004bd380` callback when replay mode is greater than `1`. It checks the per-participant sample counter at `007a3e30 + participant*4`. When that counter is zero, it tests the byte at `007a5f48 + 007cda54`; a zero byte sets replay state `4` and skips decoding. Otherwise it calls `004bcee0` with a 128-byte stack destination and then copies exactly `0x80` bytes to `007cd548 + participant*0x80` (`ev_39b2f81091c5e1fb6c9045456b2b47f9476a6f405c348cf5d74e03d723260b0c`). It then advances the participant sample counter and resets it when it reaches `0x20`.
2. `004bcee0` makes four sequential calls to `004bca80`, each using compressed source `007a5f48 + 007cda54`, a 32-byte logical output count, and a per-call consumed-source count. After each call it advances `007cda54` by that consumed-source count. It copies only the first 32 decoded bytes of each channel into the corresponding 32-byte channel slot in its local 128-byte result (`ev_55e2a41b874ed991a9dfb60cd902b3b27069e162aef93ee95c6979d9e5272100`).
3. The primitive `004bca80` receives no input length or end pointer. It reads control/literal bytes directly from the compressed source until its produced-output counter reaches at least 32; the output-count check is between complete token runs. The established malformed-token arithmetic allows one channel to produce up to 159 bytes before it exits, while zero-control tokens consume source bytes without increasing output. Therefore the 32-byte destination slot is not enforced by the primitive. Its output scratch begins at `007a3e10`; the next known globals include the participant counters beginning at `007a3e30`. An overlong run can cross the intended 32-byte staging area into adjacent state. The precise allocated scratch-object extent is not separately declared by the binary; the address adjacency and following counter uses are direct static facts.

## File producer, reader, header, and extent distinctions

- The replay load path is `004bcb00 -> 004bd2e0 -> 004e28d0/open -> 004e2de0/read -> 004e3ae0/ReadFile -> close -> validators 00478090/00478100`. `004bd2e0` requests up to `0x296f8` bytes into buffer `007a3e50` and then validates the fixed header/metadata (`ev_f98e1b2d9e98aab2dba9251ae017a93d4e0fad044d206f4139389a20a5bac7a6`). The file backend clamps each read to its recorded file length and requested byte count; a short read returns the actual count. The caller does not preserve or compare that count before running the validators. Open failure returns failure; a nonzero read/validation path can proceed even though the RLE decoder later has no retained actual-byte boundary.
- Header validation checks a fixed first DWORD value `0x20f0` and selected metadata fields; it is not a check that the compressed stream is fully present. The payload stream starts at `007a5f48`, offset `0x20f8` from `007a3e50`. On successful load, `004bcb00` copies metadata, sets replay mode, and resets the playback cursor `007cda54` to zero. It does not set `007cda54` from a compressed-length field, nor store the read return count as an end pointer.
- The field at `007a5f44` is copied to `0055fe40` as metadata. It is not used here as the compressed input extent. `007a5f40` is likewise used as a flag/mode field. Distinct values must not be conflated: `007a3e30 + participant*4` is a per-player 0..32 sample counter; `007cda50` is the recorder's accumulated compressed-output cursor; `007cda54` is the playback compressed-input cursor; and the file backend's record `+0x1c` is the actual file size used to clamp reads.
- The matching save path `004bd1e0` copies `0x20f0` bytes of replay state to `007a3e50`, fills metadata at `007a5f40/+0x44`, then calls the save wrapper with buffer `007a3e50` and fixed byte count `0x296f8`. The wrapper opens the replay file and delegates that buffer/count pair to `WriteFile` (`004e2e20 -> 004e3cc0`; see `004bd1e0` and `004eeae0` assembly). This is a fixed-capacity file write, not a stored compressed-stream length. The stream is terminated on playback by the zero-byte sentinel check in `004bd090`; no serialized compressed cursor is consumed as an input bound.
- For a full-size `0x296f8` input, the requested read interval from `007a3e50` ends at `007cd548`, exactly the start of the per-participant output rows. Shorter files leave the remainder of the global input area untouched by the read. Because actual read length is discarded and the decoder cursor is not compared against it, safe playback still depends on the byte stream's own zero sentinel being present within the bytes actually read before any out-of-file or aliased state is consulted.

## Error, EOF, and conditional safe playback domain

- If replay open fails, `004bd2e0` reports failure and `004bcb00` sets playback state and participant count back to zero. If open succeeds but the read is short, its count is not used to bound decoding. The format validators can reject bad metadata, but no source-length rejection was found in these callers.
- At a block boundary, `004bd090` treats a zero byte at the current compressed cursor as EOF/error, sets replay mode `4`, and skips the decoder. Within a block, however, a zero token is accepted by the primitive as a zero-output token; it advances the source cursor and continues. The boundary sentinel is therefore not a general bounds check for every token read.
- Safe playback requires all of the following: participant index from object `+0x1f4` indexes a valid initialized row and counter; each decoder invocation has enough actual bytes for every control/literal byte it reads; the cursor remains within the stream bytes returned by the file reader; and each channel's complete runs do not write past the intended 32-byte staging slot before its post-run output-count exit. The code establishes the fixed local destination size and state checks, but does not enforce the source extent or exact output extent. No malformed file was executed, and no runtime corruption is claimed.

## Evidence and remaining boundary

Primary REA evidence includes decoder and wrapper assembly/pseudocode `ev_2441da83012ff56c4011f069c14aa42a5d29a6ed4ba769595054430a6846154`, `ev_55e2a41b874ed991a9dfb60cd902b3b27069e162aef93ee95c6979d9e5272100`, playback caller `ev_63f1d6a14a8e5b6a0c8ff5981a10b01429bf3b6cdd13264d3ca8fd3fb33f4bdd`, recorder `ev_9be253355e4d88011cedbe81f40167ac79f80e2477666cd34a6e3137a06e44af`, append wrapper `ev_bda8f8b7c7c8dde50fb3f18791344e81d1d71ce8ef8f20b73b131c70d3089fc3`, and playback file load `ev_f98e1b2d9e98aab2dba9251ae017a93d4e0fad044d206f4139389a20a5bac7a6`. The pre-existing static RLE probe remains limited to output arithmetic (`input_extent_bound: null`) and does not establish hostile-file reachability or actual gameplay pattern frequency.

Still unresolved are the upstream index admission for object `+0x1f4`, actual short-file/trailing-byte contents on the installed runtime, whether any other loader validates or clears the whole input region, and whether all four channel patterns capable of expanding co-occur in normal input. Those gaps do not alter the static absence of a compressed-byte-count check in this decoder call chain.
