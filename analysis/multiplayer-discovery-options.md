# Multiplayer discovery and join options

## Scope and result

This is a bounded static map of the installed NFS III build, SHA-256 `2a20f80465ed53d320f1a6f41c9dde2c07de0bc5525af1f23f8e6aff3e6181fb`, its installed frontend menus and English text table, and its direct executable imports. The worker pass made no game, network, configuration, executable, or persistent Ghidra changes; parent project annotations are described below. No external server was queried, and no provider DLL was loaded for this audit.

The installed menus expose distinct IPX game-list actions and TCP host/manual-join controls. IPX has a visible `Games Available` list with Create, Join, and Refresh actions; its code refreshes a provider-owned game list and joins a selected record. TCP's in-binary dialog has Host Game, Join Game, and port selection; the join dialog accepts an IP address or domain name. The exact packet-level discovery mechanism behind the IPX list was not recovered, so “Refresh list” establishes game-list enumeration but does not, by itself, prove broadcast versus a provider/master query. The build contains legacy NPS service hooks, including server-list API names, but this pass found no proven public-lobby UI route or active master server. Tournament strings and menus establish game/tournament UI, not an online tournament service.

## Menu path and providers

### Connect Players entry

- Installed `FEDATA/MENUS/setup.mnu` labels the `[button]` entry `Connect Players` (`codelink=SETUP_CONNECTPLAYERS`, `nextmenu=connect`).
- Installed `FEDATA/MENUS/connect.mnu` offers, in order: `Network TCP` (`codelink=tcp`, `nextmenu=mainmult`), `Network IPX` (`codelink=ipx`, `nextmenu=ipx`), `Modem`, `Serial`, and `RaceNet` (each `nextmenu=mainmult`). In active `nfs3.exe`, initializer `004405c0` maps TCP to `0043fe50`, modem to `0043ff50`, and serial to `0043fee0`. Its RaceNet callback assignment is absent in this build; RaceNet remains unresolved. See [connect menu dispatch crosswalk](connect-menu-dispatch-crosswalk.md). Static registration does not prove successful connection.
- `FEDATA/MENUS/ipx.mnu` exposes `Create game`, `Join game`, `Refresh list`, and a `Games Available` selection list. This is a concrete built-in discovery/join UI.

### IPX game-list path

The binary's entry-initialization code looks up `joingame`, `creategame`, and `refreshlist` strings and assigns handlers at menu-item `+0x64`: `joingame` points to `0043fdd0`, `creategame` to the setup dialog at `00440040`, and `refreshlist` to `004400b0`. The `joingame` handler reads the selected row from the populated list, prepares its endpoint fields, and calls `JoinSelectedNetworkGameAndAwaitRoster` (`0049e800`). The `creategame` setup dialog registers `HandleNetworkSetupMenuSelectionCallback` (`0043f640`), which opens the transport/session selection UI. REA evidence: code-link xrefs `ev_2dd64f9d7f3f68adffff188ec3eae293e05e0fe83e1f1067f92b09640785ba8b`, `ev_cfa12f960e6e1e8fd7606701f32aac9cf90087cf9b0525c0352b154cf8acae99`, and `ev_0e77ee4d0b5caaa0b00f3149296c1338edf8de4cebd7d3522f3314c5b7d14334`; byte evidence for the registration block `ev_67d824fcda5e48b6bd35f9a86ff2d63a9131a02767d710c29c7b563c200ea49f`.

`Refresh list` calls `0043f220`, which replaces the UI list from the result of `0049e3d0`; that routine selects the current network-service object and invokes its operation table's method at `+0x10` before consuming/sorting the returned `0x40`-byte game records. REA evidence: `0043f220` `ev_80d221a4d1320dbc8d6064e1dd24d02475ff5aee7c596407d07a62ceffb6d8c7`, provider enumeration `0049e3d0` `ev_e06010a028d3a15251de39a1f6d27947850178b217c6c31cd0a9247d20b96656`, service dispatch `004f4eb0` `ev_dc17f7c91fb2ef84b5a59c319798749f755b9c6f6b798f8d9cf9abc9cdf74e45`, and selected-record join `0043fdd0` `ev_079970c011ede3335385e8ff8c79701ae531bfcfd1df737e2c556d5cd8166f58`.

The installed binary has IPX-specific implementation strings (`win\\ipx.c`, `ipxopensocket`, `WINIPXSend`, `WINIPXRecv`) with code references in the connection layer. It also has an unreferenced display string `DirectPlay IPX`; the PE does **not** directly import a DirectPlay DLL. The direct import table includes `WSOCK32.dll`. I therefore identify the menu/provider as the installed IPX game-list path, while leaving its exact discovery wire protocol and any DirectPlay involvement unresolved.

### TCP host, manual join, and port selection

A separate in-binary TCP connection dialog is initialized at `0043fe50`; it uses localized text IDs `0x10` (“TCP Connection”), `0x15` (“Host Game”), `0x17` (“Join Game”), and `0x78b` (“Port”), and registers callback `0043f760` (REA raw-byte evidence `ev_53df230cc85b1db7db56dcb92095d143bc8e8ec488162feadcea2dba5caed675`, `ev_cb42f8eb32c924ee0a69ce079c891701d9b56f29428404e1859826101f695a56`). The callback's first two menu choices take separate branches:

- **Host Game:** retries initialization with the configured/default network suffix, then opens `InitializeNetworkTransportSelectionMenu` (`0043f320`) and its session callback (`0043f7e0`). The later host/session setup is conditional on selecting a valid service/transport and succeeding; the inspected static code does not establish that any provider is installed or reachable.
- **Join Game:** retries the selected port value, then opens `InitializeNetworkServiceSelectionDialog` (`0043f4e0`) with `HandleNetworkServiceSelectionCallback` (`0043f680`). The English text table resolves ID `0x0a` to “Enter IP address or domain name:” and ID `0x0b` to “Press escape to cancel”. On confirmation, the callback passes the entered string to `BuildNetworkEndpointFromMutableAddress` (`0049ea70`), then to `JoinSelectedNetworkGameAndAwaitRoster` (`0049e800`). The address helper accepts a textual host and optional colon suffix, applying the configured/default suffix when absent; no live DNS lookup or connection was attempted.
- **Port choice:** the TCP dialog's third choice alternates the configured suffix and refreshes the displayed localized `Port: <number>` label. Installed English text ID `0x78c` reads “1030 is legacy, 9803 is modern.” Static helper defaults zero to `0x264b` (9803); the installed `readme_en.txt` recommends 9803 and documents 1030 compatibility. This describes port selection; it does not demonstrate that a particular host is reachable.

Thus TCP is manual host/domain entry rather than an in-menu automatic host list. The same address route can be used for a LAN host or an internet host when the host address, selected port, firewall, and routing permit it. The installed readme discusses host port access/forwarding. This audit did not test that route. Active `nfs3.exe` statically connects the `connect.mnu` `codelink=tcp` item to `0043fe50` through `004405c0`; no live UI transition or successful session was observed.

### Modem and serial

The active `connect` initializer registers the Modem and Serial item callbacks as `0043ff50` and `0043fee0`, respectively (see [dispatch crosswalk](connect-menu-dispatch-crosswalk.md)). The binary also contains TAPI modem and indexed COM-port paths, and the installed English labels include “Modem Connection”, “Serial Connection”, and “COM Port”. The modem callback's menu-enabling check queries the current modem/list state; its underlying modem-name population and current hardware/provider availability remain unresolved. Static callback registration establishes the built-in route, not that compatible hardware is present or the feature succeeds on a current system.

### RaceNet and NPS service hooks

In active `nfs3.exe`, the RaceNet item has no callback store in initializer `004405c0`; the flag-controlled block contains a jump over NOP padding where a backup build had such a store. Its configured `nextmenu` is `mainmult`, but the active click route is unresolved. Separately, the binary dynamically reads a DLL path from `HKLM\\SOFTWARE_EA_NPS_DLL`, calls `LoadLibraryA`, and resolves an NPS API family including `NPSConnectToServer`, `NPSGetServerList`, `NPSGetServerInfo`, `NPSLocatePlayer`, `NPSGetUsersOnServer`, `NPSStartGameServer`, and user/channel operations (`004a5880`, `004a54f0`; evidence `ev_e08deb6b708d9b17676d82ce4c11e9a3e59601fdd6bda4b6c3f97e04f954b446`, `ev_a059dea6d0124842f91bd6b08f8f2b47a75bc14e82bd615b7836a4bd196cf533`). This is a legacy external-provider interface surface with server/lobby-capable API names. In the bounded direct-xref review, the selected server-list/user/server pointer globals had references at their `GetProcAddress` assignments only; no active public service provider was established. A stored export name is not proof of an operating public lobby.

No NPS DLL is directly imported by `nfs3.exe`; its direct import is Winsock. The executable can dynamically load an external provider selected through registry configuration, but no such provider file was inspected. The network service selection code also has provider-candidate and suffix fallback logic; provider identity and current availability remain unverified.

## Public lobby, tournament, and discovery conclusions

- **Automatic discovery:** IPX screen has a game list and refresh action, and its refresh path enumerates records from the selected service object. The exact discovery packet and broadcast/multicast/server-query mechanism were not resolved. TCP uses manual host/domain entry, with no corresponding TCP “Games Available” UI in the inspected menu.
- **LAN:** IPX is the explicit legacy game-list choice. The custom TCP path can use a local address and port, but automatic LAN broadcast for TCP was not found in the UI/code path reviewed.
- **Internet host:** TCP text entry accepts an IP/domain name and allows a selected port, so direct internet-host joining is supported at the UI/provider boundary. Host-side public reachability and connection success were not tested; installed documentation explains port/firewall requirements.
- **Public lobby/master server:** NPS export names provide legacy server-list/server-info/player-locate hooks, but no active public lobby, master endpoint, current provider, or reachable `RaceNet` menu route is established. No external service was queried.
- **Tournament:** installed UI/resource strings include tournament and tournament-standings/save/load material. I found no tournament-specific entry in the resolved NPS export family and no established network tournament registration/query path. This is a bounded search of the selected executable's menu strings, direct code references and NPS export-name resolver, not a claim that every indirect/external provider capability is absent.

## Search boundary and limitations

Reviewed: the active selected executable's menu/callback and service-selection paths noted above; direct PE imports; installed `connect.mnu`, `ipx.mnu`, `mainmult.mnu`, `setup.mnu`, `text.eng`, `readme_en.txt`, and `ip.cfg`; and direct xrefs to exact codelink/API strings and stored NPS server-list pointers. TCP codelink mapping is statically resolved; RaceNet callback dispatch is not. The earlier crosswalk briefly treated a callback in `nfs3_org.exe` as active evidence; the corrected [crosswalk](connect-menu-dispatch-crosswalk.md) now distinguishes the backup from active `nfs3.exe`. Not reviewed: registry contents, external provider DLLs, network packets, live UI transitions, server availability, all indirect callback aliases, or every external plugin. Remaining uncertainties include provider-specific IPX protocol, RaceNet click behavior, provider identity, and public service availability.
