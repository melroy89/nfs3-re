# Controller action label crosswalk

## Result

The installed PC controls UI and input path statically identify evaluator slot 2 as **Accelerate** and slot 3 as **Brake**. The same ordinal is used by the controls-page row, the configuration DWORD, and the runtime evaluator slot:

| UI row / config DWORD | UI label ID and installed English text | Built-in keyboard default | Runtime evaluator | Buffered sample |
|---:|---|---|---:|---|
| 2 / `record+0x08` | text ID `0x48`: `Accelerate` | packed `0x00004804`: type `4`, key code `0x48` (`Up`) | slot 2 | byte `+1` |
| 3 / `record+0x0c` | text ID `0x49`: `Brake` | packed `0x00005004`: type `4`, key code `0x50` (`Down`) | slot 3 | byte `+2` |

These are action labels in the installed control-remapping UI. The default key assignments are replaceable configuration values; they do not identify physical axis positions, prove the current `config.dat` is selected, or prove which labelled action supplies either physics field after mode/profile transformations.

## Remaining eight action-mask bits

The collector first evaluates slots 0–3 into the four buffered sample bytes. It then iterates eight times over evaluator slots 4–11, setting mask bit `1 << iteration` when the corresponding evaluator returns nonzero. Therefore collector bit `b` corresponds to evaluator slot `4+b`. The configured mapping below follows the controls-page row dispatcher at `0043c8c8` (row ordinal to text ID), the installed `text.eng` labels, and the mode-specific binding setup at `0048f1f0` (record DWORD to evaluator slot). Rows are displayed in controls-page ordinal order, not reordered by evaluator slot:

| Collector mask bit | Evaluator slot | Controls row / record DWORD | Label ID and installed English text | Embedded single-player fallback |
|---:|---:|---:|---|---|
| `0x01` | 4 | no writer in reviewed mapping | unresolved | none established; slot array is cleared before setup |
| `0x02` | 5 | 10 / `record+0x28` | `0x51` Reset | `0x52001304` (R) |
| `0x04` | 6 | 4 / `record+0x10` | `0x4a` Handbrake | `0x20003904` (Space) |
| `0x08` | 7 | 8 / `record+0x20` | `0x4f` Horn (Siren) | `0x48002304` (H) |
| `0x10` | 8 | 5 / `record+0x14` | `0x4b` Shift up | `0x41001e04` (A) |
| `0x20` | 9 | 6 / `record+0x18` | `0x4c` Shift down | `0x5a002c04` (Z) |
| `0x40` | 10 | 12 / `record+0x30` | `0x50` Lights | `0x4c002604` (L) |
| `0x80` | 11 | 11 / `record+0x2c` | `0x1bc` Spike strip | `0x53001f04` (S) |

This resolves the important `0x04` path: row 4 is labelled **Handbrake**, its configured binding is written to evaluator slot 6, and slot 6 produces collector mask `0x04`. `UpdatePlayerVehicleControls` (`00431430`) tests that bit at `004314cf` and writes a Boolean to vehicle byte `+0x50d` at `004314e7`. Thus the `+0x50d` control is reached by the labelled Handbrake action in this configured-input path. This does not establish that every producer of `+0x50d` represents Handbrake, nor that the installed user configuration selects the built-in Space binding.

The same setup maps row 10 Reset to slot 5, row 8 Horn to slot 7, row 5 Shift up to slot 8, row 6 Shift down to slot 9, row 12 Lights to slot 10, and row 11 Spike strip to slot 11. The table at `0043c8c8` dispatches row ordinals to numeric text IDs; the installed English resource resolves those IDs to the shown strings. The setup's mode-specific mapping uses `record+4*row` and writes the packed value to `0079c340+4*slot` through `0048f940`. The collector then maps slot `4+b` to bit `b` as described above.

The action-latch filter at `0048f6a0` retains bits selected by mask `0xf2` and clears those selected bits from the current mask before the next sample. In particular `0x04` is not in `0xf2`, so the Handbrake bit is not suppressed by this rising-edge latch filter and remains level-sensitive on this replay/sample route. Bits `0x02`, `0x10`, `0x20`, `0x40`, and `0x80` are in the retained mask; bits `0x01` and `0x08` are not. This describes the filter implementation, not a claim that every input mode necessarily traverses it.

The embedded two-player defaults differ by player row: player 1 defaults Handbrake to Insert, Shift up to Page Up, Shift down to Page Down, Horn to M, Reset to End, Spike strip to P, and Lights to L; player 2 defaults them to Space, A, Z, W, X, S, and Y respectively. These are fallback table contents, not evidence of current configuration selection.

## Menu label to displayed row

The installed `FEDATA/MENUS/control1.mnu` opens the control settings page and links the Dead Zone, Force Feedback, Audio Feedback, Function Keys, predefined controls and reset entries. Its file does not enumerate the thirteen remapping rows. The action rows are generated by the executable's decoded control-page renderer at `0043c900` (the region is not a defined function in the current analysis database).

The renderer loops an ordinal from 0 through 12, dispatches through the 13-entry table at `0043c8c8`, and passes the selected numeric text ID to `RenderFrontendControlBindingLabel` (`0043c110`). Table entry 2 resolves to the small case block at `0043cbf2`, which supplies ID `0x48`; entry 3 resolves to `0043cbf9`, which supplies ID `0x49`. In the installed English text resource `FEDATA/TEXT/text.eng`, numeric IDs `0x48` and `0x49` resolve to the NUL-terminated strings `Accelerate` and `Brake` respectively. This confirms row labels from the installed renderer and localization data, rather than inferring names from physics uses.

For each ordinal `i`, the same render loop obtains the configuration binding from the selected mode's mapping base plus `4*i`, then passes that packed binding to the binding-label renderer. In two-player mode it also renders the parallel record beginning 13 DWORDs later (`+0x34`). Therefore row 2/3 label placement is tied directly to record ordinal 2/3; the labels are not merely adjacent text with an assumed ordering.

## Capture and configuration record mapping

The control-page input callback body beginning `0043cf80` handles pending binding capture. The selected control ordinal is used to form a DWORD destination at `mapping_base + 4*ordinal`; when a candidate packed binding has been captured and resolved against conflicts (`ResolveFrontendKeyTransitionCode`, `0043ce80`), the callback stores it through that destination. The callback's active-capture state is separate from the ordinal-derived destination. This is a decoded code region, not a Ghidra-defined function boundary; the report does not assign it a new function identity.

Mode-specific mapping base selection is explicit in helper `004904d0`:

- `006fd3b0 == 1`: base `006fd240`, a two-player mapping area with 26 DWORDs (two 13-DWORD rows, stride `0x34`).
- Otherwise: base `006fd20c`, the single 13-DWORD row.

The runtime setup at `ApplyConfiguredBindingsToActionSlots` (`0048f1f0`) selects the mode-specific base and maps each source record field to evaluator slots. For a record base `R`, the input sequence includes `R+0x08` assigned with evaluator index 2 and `R+0x0c` assigned with evaluator index 3 (`0048f254..0048f269` in the first two-player row; corresponding writes repeat for the second row). The non-two-player path has the same field-to-slot assignments at `0048f3f8..0048f40d`. The slot writer at `0048f940` stores the supplied packed binding at `0079c340 + 4*slot`. Thus the UI/config ordinal 2 or 3 is carried through without reordering into evaluator slot 2 or 3.

`CollectBoundPlayerInputsAndActionHistory` (`0048f550`) reads the first four evaluator entries in order. It places the return from slot 2 in sample byte `+1` and the return from slot 3 in sample byte `+2` (`0048f5fc..0048f62d`). These bytes are then carried in the four-byte buffered player sample. The earlier controller audit traces byte `+1/+2` through `UpdatePlayerVehicleControls` to vehicle bytes `+0x504/+0x505`; this crosswalk now supplies the direct UI labels for those two channels.

## Built-in fallback defaults

The executable contains a 13-DWORD default table at `00490430` and a 26-DWORD two-player default table at `00490464`. The default-construction helper at `00490c40` copies these table extents and selects the appropriate layout for its input mode. In both arrays, entries 2 and 3 are:

- entry 2: `0x00004804` (binding type byte `0x04`, key code `0x48`);
- entry 3: `0x00005004` (binding type byte `0x04`, key code `0x50`).

`WriteFrontendKeyboardBindingLabel` (`0043d7f0`) recognizes low-byte binding type 4 as keyboard input and maps key codes `0x48` and `0x50` to localized IDs `0x60` and `0x61`. The installed `text.eng` strings at those IDs are `Up` and `Down`. This verifies the built-in fallback label chain: default `0x4804` displays Up for Accelerate, and default `0x5004` displays Down for Brake. The tables show the executable's fallback/default values; they do not establish that no user configuration overrides them.

The installation's `config.dat` was not parsed into these 13-DWORD records in the prior bounded controller audit. Consequently the evidence identifies the action labels and embedded fallback assignments, but not a selected player's current live binding values.
