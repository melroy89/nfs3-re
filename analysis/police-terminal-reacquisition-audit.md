# Police terminal-target reacquisition and stop-table audit

## Scope and target

Static analysis used the selected `nfs3.exe`, SHA-256 `2a20f80465ed53d320f1a6f41c9dde2c07de0bc5525af1f23f8e6aff3e6181fb`, through an ephemeral REA/Ghidra session. No executable, runtime, or persistent Ghidra changes were made. Existing stop-limit and runtime lifecycle records are in [detailed-analysis-notes.md](detailed-analysis-notes.md#pursuit-roles-budgets-and-stop-lifecycle).

For the added field cross-check, the entire selected executable's disassembly was searched read-only with `objdump -d -Mintel --no-show-raw-insn <exact nfs3.exe> | rg -n -i 'mov +DWORD PTR \[[^]]+\+0x(2c4|6e0)\]'`. This records decoded direct base-plus-offset stores; it is not a proof against aliased/register-computed writes or indirect callbacks.

## Target and officer counters are distinct

`FinalizePoliceStop` (`00401ff0`) operates on an officer with group pointer `+0x628` and target pointer `+0x624`. It increments the officer's `+0x2cc` counter and compares that new value for **equality** with `006fd4b8`; equality updates officer `+0x2d4`. Separately, it increments the stopped target's `+0x2c8` counter, compares the new target count with `g_nPursuitStopLimit` (`006fd4bc`) using signed `>=`, and writes target state `+0x2c4 = 4` when the limit is reached.

The target's post-increment `+0x2c8` is also used directly as a 16-byte row index at `005521b4 + 16*count`; there is no local clamp. That table has ten rows, indices 0..9, followed by a separate voice map. The `+0x2cc` officer counter does **not** index this table. Finalizer dossier `ev_0e4a5f50dc0abe3a2d6b592b72a2e6ebaa5140c5e07daeb1911a9cd87eed97de`; ten-row bytes/extent are recorded in the existing lifecycle notes.

### Bounded AI-controller transition relation for a terminal result

For fixed same-object terminal result `+0x2c4 == 4`, controller states `S ∈ {1,2,3,4}`, and byte `+0x200` bit `0x01` set, `00409c00`'s own callback preserves the state set `{1,2,3,4}`. This is a local transition relation, not a global invariant:

| Entry state | Gate and same-case writes | Callback exit state |
|---|---|---|
| 1 | Initial `0040df10` or state helper `00404b90` can return early and preserve 1. Otherwise phase test may set 5, terminal-result check overwrites it with 4, then `00409a90` true writes 2; false leaves 4. | 1, 2, or 4 |
| 2 | Initial `0040df10` or `00404b90` can return early and preserve 2. Otherwise phase test may set 5, terminal-result check overwrites it with 4, then `00409a90` false writes 1; true leaves 4. | 1, 2, or 4 |
| 3 | Initial `0040df10` can return early and preserve 3. Otherwise the terminal-result check writes 4; `00409a80` is constant 1 and the case overwrites it with 1. | 1 or 3 |
| 4 | State-4 case updates its timer fields and returns without writing `+0x6e0`. | 4 |

If bit `0x01` is clear, the terminal-result check is skipped. A phase test can then leave the intermediate state 5 in some paths, so the stated set bound does not apply. The operand-wide disassembly search found no explicit `+0x6e0` store in the direct callees used by cases 1–4; other decoded direct-field stores in the executable are at `004056f1`, `00405782..004059e0`, `00409b4a`, `0040bf95`, and `0040cbe5`. This supports the transition table against explicit base-plus-offset stores in those cases, while leaving aliasing/indirect writes and callbacks outside this function scope unproven.

After common stop cleanup, the shared group is phase 0 and has member count 0. Because target `+0x628` is not cleared by attachment/finalizer cleanup, if the AI controller is in state 6, its state-6 path calls `00401500`, observes phase not 2, writes `+0x6e0 = 1`, then observes zero member count and calls `00409b40`, which writes 1 and leaves group phase 0. **State 7 differs:** AI controller jump-table entry 7 goes to `00409fdb`, which only copies the current tick into object `+0x704` and returns. It neither checks group phase/count nor changes `+0x6e0`; state 7 therefore persists across this callback after cleanup. `ResetPlayerPursuitStopState` (`004056e0`) belongs to the separate police state machine `00405740`; its state-6/7 branches reset the police-controller object, not the stopped racer's AI-controller case 7. The AI state-6 transition is sufficient for the next callback if it runs and target `+0x628` still points to the cleaned group. It does not establish that the callback runs before replacement or that no separate reset/indirect writer changes the object.

### Retained human-target callback path

The retained human target uses callback `00431430` at object `+0x600`; this is distinct from AI callback `00409c00`. In its bytecode, EAX is copied to ECX as the current object. Before invoking the callback at `+0x5fc`, it calls `00405740` with that same object in EAX when any of these gates is true: `005efd98 > 0`, `005efd88 > 0`, or `006fd494 != 0` (`00431438..0043145a`). Therefore a temporary category-bit change does not by itself prove that this retained human callback was replaced or that `00405740` runs on every invocation. Callback selection and this conditional dispatch must be read from the stored pointer and the listed globals for the relevant target.

When the human target's `00405740` does run, EAX is the target object and the routine sets EDX to that same pointer before dispatching on its `+0x6e0`. Its state-6 case (`00405920..004059af`) does not read its own result `+0x2c4`. It first requires the short field `+0x164 == 0` and several motion/timing conditions to reach the group-count branch. If they fail, state 6 is retained. If they pass and shared-group member count is nonzero, it writes state 7; if count is zero, it calls `ResetPlayerPursuitStopState` (`004056e0`). After ordinary finalizer cleanup has set that shared group's count to zero, this means a state-6 human target exits to state 2 only on a callback whose motion/timing gates reach the reset branch; the source has no unconditional terminal-result-4 transition.

The human target's state-7 case (`004059b0..00405a11`) also does not inspect its own result `+0x2c4`. After common cleanup has put group phase `+0x1c` at zero, `00401500` returns false, so the routine writes `+0x6e0 = 2`, clears the object's `+0x200` bit `0x02`, and calls `00429100`; because member count is also zero, it then calls `004056e0`, which again sets state 2 and group phase 0. This is unlike AI callback state 7, which only refreshes `+0x704` and persists. On the linked officer's `CheckPoliceStopConditions` path (`00405630`), the target result check rejects value 3 in a flag-gated branch, not value 4; if the target's `+0x6e0` is still 6/7, the subsequent `00405430` gate can approve it. Consequently result 4 does not itself bar a human target from the phase gate before its conditional `00405740` update runs. Whether the callback runs before reacquisition, and whether the state's motion gates permit state-6 retention, are unresolved scheduling/runtime questions.

The direct `+0x2c4` stores from that scan have distinct paths. Terminal finalization at `0040209e` writes 4 to the stopped target. `UpdateParticipantLapProgressAndRaceState` (`004ce280`) writes 3 at `004ce4bd` only after a result-4 guard (`004ce498..004ce49f`) has passed; a separate path at `004ce50f` writes 3 when byte `+0x200` bits `0x20` and `0x04` are set, `+0x2cc` equals `006fd4b8`, and current result is not 3. ## Table-index bound on the ordinary completed-stop path

For the documented setup domain, local single-player and network modes use lap count plus one for racer targets and one for human-police targets; split-screen uses one when both humans are police and otherwise lap count plus one. With menu lap choices 2/4/8, the largest ordinary target stop limit is 9. Given target `+0x2c8` reset to zero, exactly one finalizer invocation per completed stop, and no counter mutation, the terminal invocation increments `8 -> 9`, sets `+0x2c4 = 4`, and reads row 9, the last table row. A later index-10 access is excluded only if reacquisition/finalizer reentry is excluded by some additional lifecycle invariant; this audit has not established such an invariant because the reviewed phase gate tests the distinct `+0x6e0` field.

This is a conditional bound, not a complete lifecycle proof or local safety check. `FinalizePoliceStop` will read whatever row its incremented target count names if called; neither its body nor `00401fb0` clamps the count. A repeat finalization, externally changed target count, stop limit above 9, or direct/unresolved state-5 writer can create an out-of-range index. The officer counter `+0x2cc` remains a separate equality threshold and is not the cause of the table index.

## Remaining runtime and static gaps

The retained asynchronous ticket traces show a configured limit of 3 and target `+0x2c4`/controller `+0x6e0` samples of 0 at the captured boundaries, with completed-stop count rising only to 1 or 2. Their own metadata says capture starts mid-stop and has no instruction tracing. They do not sample the terminal `8 -> 9` example, establish the order between finalizer and callback dispatch, or show whether a terminal candidate passes the replacement gate. Relevant files: `analysis/evidence/runtime/racer-ticket-completion.json`, `racer-second-ticket.json`, and `racer-ticket-in-progress.json`.

Static instructions show distinct callback-specific outcomes. For the AI callback, terminal result 4 and bit `0x01` keep states 1–4 within {1,2,3,4} after early returns and last-writer precedence; after cleanup, AI state 6 exits to 1 if it still points at the reset group, while AI state 7 persists. For the retained human callback, `00431430` conditionally invokes the police state machine; after cleanup, human state 6 can remain 6 if its motion/timing gates do not reach the zero-count reset, while human state 7 exits to 2 when the update reaches that case. In both paths, a replacement attempt can precede the next relevant callback, and result 4 does not itself fail the linked-target state-6/7 gate. The evidence does not establish callback order, callback-pointer stability, or controlled replacement admission. No live state was inspected to verify callback selection, object flags, group phase, target links, current stop limit, or target count at reacquisition. Stop limits above the standard 2/4/8 setup-derived domain and external/indirect writes to target `+0x2c8` remain separate open questions.

**Conclusion:** the target and officer share a group pointer at attachment, while only the officer is stored in the group member array. Finalizer cleanup resets that group's phase and member count but does not clear target `+0x6e0` or target `+0x628`. AI and retained human controllers have different state-6/7 behavior: AI state 7 persists in its callback; human state 7 transitions to 2 after the zero-count cleanup, while human state 6 resets only if its motion/timing gates reach that branch. The retained human callback conditionally calls `00405740`, and no callback ordering relative to replacement is established. Because result 4 does not itself fail the phase gate, no universal proof establishes that terminalization prevents another finalizer call. Under the standard 2/4/8 lap domain and one-finalizer-per-stop progression, the last table access is row 9; enforcement of that progression after terminalization remains unresolved, and the finalizer itself has no index clamp.
