# Lap-count admission and per-lap storage audit

## Scope and evidence

Target: PC nfs3.exe SHA-256 `2a20f80465ed53d320f1a6f41c9dde2c07de0bc5525af1f23f8e6aff3e6181fb`. Parent live Ghidra review of004ce280/004ce5a0 corroborated the old-index timing store, signed metric fence, count-controlled initializer and index8 aggregate alias.

This audit follows the decoded lap-count DWORD `006fd4b4` into live vehicle lap bookkeeping, the initializer, race progression, and saved-result storage. It uses the shipped `nfs3.exe` static findings recorded in [lap-count-producers.md](lap-count-producers.md), [stored-records-contract.md](stored-records-contract.md), and the Issue #7 trace in [detailed-analysis-notes.md](detailed-analysis-notes.md#decoded-lap-count-direct-reference-census--issue-7). No runtime execution or executable/database modification was performed.

## Admission into gameplay

The decoded total is a DWORD. The ordinary frontend decoder reads only the low WORD of a separate selector at `006fd4b0` and maps selector values `0`, `1`, and other to totals `2`, `4`, and `8`. In the normal setup menu loop, `ReconcileRaceSetupMenuConstraints` runs before input/action dispatch. Thus, when that reconciliation path controls race launch, the per-lap indices requested by the total are `0..1`, `0..3`, or `0..7`.

That is not a universal admission rule. Other observed writers are: mode 1's `2` or `4`; mode 2's `2`; a zero-extended network packet BYTE (0..255); and the supplied transport setup's full DWORD from `-LAPS`. The `-LAPS` parser has no local 2/4/8 comparison, although the ordinary setup loop later normalizes the selector before a UI-driven launch. Type-2 network settings copy the wire BYTE directly into the DWORD, and the packet path itself does not establish a gameplay cap. Replay/ghost bulk-copy paths and the playback-loaded handoff also remain outside a proved common validation gate. See the producer report for ordering details and limits.

## Live lap index and progression

`InitializeVehicleRaceState` (`0042bcb0`) clears vehicle `+0x204` and initializes adjacent DWORD `+0x208` to 0 forward or 1 reverse. `UpdateVehicleTrackWrapCounters` (`0042cc20`) changes `+0x204` at directional track-boundary transitions when the `+0x208` condition permits it; its wrap bookkeeping has no comparison with `006fd4b4`. `CopyLinkedVehicleMotionState` (`00408520`) copies both counters from linked object `+0x624`, so the initialization and geometry path are not the complete writer set absent a linked-object lifecycle proof. The traced fields are DWORDs; the selector's low-WORD decoding and the packet's BYTE width do not make the live index a WORD or BYTE.

`UpdateParticipantLapProgressAndRaceState` (`004ce280`) copies the current DWORD `+0x204` to `+0x234`. Its metric update checks signed `+0x234 >= 8` and skips the `+0x298 + 4*i` float store in that case; there is no corresponding lower-bound test. A distinct lap-transition path stores the prior tick at `+0x240 + 4*oldIndex` without a local upper-bound test, then updates `+0x234`. Completion compares the new index for exact equality with the decoded total, subject to its state and flag gates; this is not an admission clamp. Therefore UI totals 2/4/8 fit the metric indices 0..7, but only if the live index remains in that range. No static check enforces that invariant at these stores.

The two base offsets are `+0x240` and `+0x298`, a difference of `0x58` bytes or 22 DWORD strides. Consequently timing index 22 aliases metric index 0 by address arithmetic. The live record has a fixed `0x9ac`-byte row, but its lap initializer writes only eight timing slots: index 8 already reaches the separately initialized field at `+0x260`, while index 22 reaches metric index 0. A count of 9 or more therefore exceeds the constructor-initialized timing slots; the count-driven access may remain inside the row's byte extent while overlapping other fields. Admission and runtime reachability remain unestablished.

## Initializer and consumers

`InitializeRaceLapEstimates` (`004ce5a0`) is called from `FinalizeRaceVehicleStates` (`004ce750`) at `004ce7c9` for an AI-category record when its `+0x200` bit `0x10` is clear and its `+0x2c4` status is not 3. Status 4 qualifies. The initializer uses the decoded signed count directly in loops over timing entries `+0x240 + 4*i` and metric entries `+0x298 + 4*i`; there is no local count clamp. Its metric loop seeds aggregate `+0x2b8` from metric entry 0 and then processes the requested count. Since `+0x298 + 4*8 == +0x2b8`, count 9 or greater makes the indexed metric sequence address the aggregate field. These are concrete within-row aliases; the call gates do not establish whether a nondefault count reaches them.

The lap-time popup (`0046d180`) and `UpdateStoredRecordsFromVehicleResult` (`00450fe0`) also scan timing entries using the configured count without a local upper cap. The popup seeds from entry 0 even for nonpositive counts. The result updater selects the minimum nonzero per-lap time and stores aggregate values into the saved-record path; it does not allocate or store one saved-record slot per lap. The metric popup scans the configured metric count and has the local eight-index-related layout concern recorded in Issue #7 notes.

For a positive ordinary UI total of 2, 4, or 8, the initializer's requested timing and metric indices are 0..1, 0..3, or 0..7. Those fit the eight explicitly initialized slots in the fixed record row, before the `+0x260` timing neighbor and `+0x2b8` metric aggregate. This avoids those specific aliases for the requested index ranges, provided the live progress index corresponds to `0..N-1`; it does not bound every consumer or guarantee that live index domain.

## Static live-record extent and initialized per-lap slots

The setup routine at `0042c700` establishes a concrete fixed backing region. Raw instructions `0042c71f..733` set `EAX=005e1120`, `EDX=0x9ac0`, then call `004e070c`; that wrapper clears the requested byte range (`004e070c..714` zeroes EBX before entering the fill loop). The next fixed region begins at `005eabe0`, exactly `0x9ac0` bytes after `005e1120`. The participant loop uses the row address `005e1120 + index*0x9ac` (`0042c789..79c`) and passes that row to `00428700`, which adds it to the participant registry at `005efac8`. Thus this pool contains 16 fixed `0x9ac`-byte live-record slots. The separate count-controlled loop at `0042c746..7bd` has no local `index < 16` test; this report does not infer the broader roster admission policy from this setup routine.

For each registered participant, the helper at `004285f0` advances EAX from the record base by `0x224` (`004285f4`). Its loop starts with EDX zero, increments before the stores, and exits when EDX reaches 8 (`00428670..67d`): it clears `vehicle+0x240,+0x244,...,+0x25c` and, in parallel, `vehicle+0x298,+0x29c,...,+0x2b4` (`0042867f..690`). The aggregate at `vehicle+0x2b8` is separately cleared by `004286ec`. The adjacent `vehicle+0x260,+0x264,+0x268` words are separately cleared before the loop (`0042861c..62a`), so timing index 8 addresses a separately initialized field rather than a ninth constructor-initialized timing slot. The helper is called for a live record in both the per-participant path at `0042c368` and the participant-wide reset at `0042c57c`; the latter obtains each record pointer from `005efac8+4*index`.

An independent original-PE-byte check of `004285f0..004286f8` (inclusive, 0x109 bytes) reports SHA-256 `a80fde2e0276f1ad50111040e916e1c9400d2cfff926f2ffdf0f77aa0208d02c`; it confirms the loop compare/increment and both indexed zero-store displacements described above.

The same `0x9ac` live-record stride is the full source and destination row length in result snapshot copying: `BuildRaceResultSnapshotsAndUpdateProgression` (`00455410`) passes the live-record registry to `00455210` and `00455280`; each copy helper sets byte count `0x9ac`, divides it into `0x26b` dwords plus the zero-byte remainder, copies that range, then increments its category count (`0045524c..272`, `004552bc..2e2`). The result snapshot bank uses 16 rows per category with `0x9ac` row stride and `0x9ac0` category stride (`00455c1f..44`); it is a separate results store, not evidence for additional per-lap slots.

This closes the earlier **backing-span** gap for ordinary live records: the eight constructor-initialized timing slots and metric slots lie inside each fixed `0x9ac`-byte row, and ordinary UI totals 2/4/8 request timing indices 0..1/0..3/0..7. It also sharpens the nondefault boundary: index 8 is beyond the timing slots initialized by `004285f0` and aliases the separate `+0x260` field; the metric initializer's index 8 aliases the aggregate at `+0x2b8`. The count-driven initializer still has no local cap, the transition writer still takes its index from live state without an upper bound, and non-menu count admission/order is still unresolved. Therefore this is a concrete 8-slot initialized layout and fixed 0x9ac-byte backing span, not proof that every nondefault path is admitted safely or that `+0x240` is a separately allocated C array.

## Bounded conclusions

- **Sufficient ordinary-menu lap domain for known metric accesses:** totals 2, 4, or 8, provided the live progress index corresponds to laps `0..N-1`. These totals stay below the `+0x298` index-8 alias and within the callback's eight-index metric fence.
- **Established for the ordinary record layout:** a fixed 16-row live-record pool with `0x9ac`-byte rows, and eight explicitly initialized timing slots per row. Ordinary menu totals 2/4/8 fit those slots when live indices remain `0..N-1`.
- **Not established:** an independent declared array type, a universal maximum total, a common pre-initializer admission gate for network/replay/supplied values, or a hard bound on the live lap index. The eight-slot initialization is not a universal runtime cap.
- **Counter width:** live progress and wrap fields are DWORDs; total laps are a DWORD. No WORD lap counter or total-lap storage was identified in these traced paths. The selector uses low-WORD semantics, while the network settings field is one BYTE.
- **Remaining evidence needed:** end-to-end admission/order proof for each non-menu producer and playback handoff, plus runtime evidence for the lap indices actually reached during ordinary results processing.
